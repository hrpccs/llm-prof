# M1 栈压缩开销曲线验证报告（CPU + 内存带宽）

> 实验：case_hotspot（单热点循环，固定工作量 ~30s），采样率 {100, 1000, 10000} Hz
> × 压缩 {off, on}，每配置 3 轮取中位数；基线 3 轮（无采样）。
> 脚本：`demo-cases/run_m1_overhead.sh`、`demo-cases/plot_m1_overhead.py`
> 复现：`/tmp/m1ov.txt`（rate mode elapsed bytes）

## 1. CPU 开销（目标进程 elapsed 相对基线 +%）

| 采样率 | off | on（-stack-compress） | 差值 |
|---|---|---|---|
| 100 Hz | +0.03% | -0.15% | 噪声内 |
| 1000 Hz | -0.55% | +0.18% | 噪声内 |
| 10000 Hz | **+2.41%** | **+1.94%** | -0.47pp（噪声内） |

- 开销与采样率**线性**（10000Hz ≈ +2%），与 rate_curve 历史数据一致；
- **压缩 on 不引入可测开销**：fp_step 每帧 ~6 指令 + 每样本 1 次 LRU lookup，
  在 10000Hz 下 < 0.5pp（低于测量噪声 ~±0.6%）；
- 结论：压缩的 CPU 成本可忽略，eBPF 侧增量不是开销瓶颈。

## 2. 内存带宽（ringbuf 内核→用户态字节率）

| 采样率 | off (MB/s) | on (MB/s) | **降幅** |
|---|---|---|---|
| 100 Hz | 0.07 | 0.04 | -43% |
| 1000 Hz | 0.43 | 0.09 | **-79%** |
| 10000 Hz | 3.95 | 0.24 | **-94%** |

- off：带宽与采样率**线性**（10000Hz = 3.95 MB/s，100Hz 的 56 倍）；
- on：带宽**近平坦**（0.04 → 0.24 MB/s，仅 6 倍增长）——增长来源是 FULL 重发
  （LRU 淘汰/新增 distinct 栈）与 STACK_ID 事件本身；
- **核心主张验证**：压缩后 ringbuf 带宽与采样率**解耦**（∝ distinct 栈变化率而非
  采样率）；高采样率场景（持续 profiling 必选）收益最大（-94%）。

## 3. 正确性（同实验内）

- on/off 样本总数一致（±0.5% 随机差，与未压缩路径相同）；distinct 栈集合一致；
- 说明：字节统计含 FULL trace（头 736B + 帧字×8）与 40B StackIDEvent；用户态
  展开 STACK_ID 走与 FULL 完全相同的聚合路径。

## 4. 局限与后续

- 单进程、单热点负载；多进程/深栈/JIT 负载的带宽解耦曲线待测（train_torch
  单点验证 -75.2%，曲线待补）；
- 10000Hz 下 ringbuf 静态预算（25.3KB × rate × CPU）已撞 2GB cap——压缩降低的是
  **生产速率/丢事件率/下游传输**，不是静态预算（见 review I3）；
- M2（时间差分聚合）预期把 on 曲线进一步压平（每窗口一条聚合消息而非每样本
  一条 STACK_ID）。
